# 性能与架构优化建议（免费 Cloudflare 套餐）

本文只提建议，**没有改动任何代码或线上配置**。依据是 `main`（含 M6）的源码阅读，**没有任何线上实测数据**：当前 `observability` 关闭，仓库里也没有延迟记录。下面标“预期”的收益都是推断，落地前先按“第 0 步”量一遍。

## 先说结论

- 页面“卡”有两类原因，需要分开看：
  1. **网络路径**：大陆访问 Cloudflare 全球网络本身就慢且不稳。免费套餐改不了，README 里“部分网络能打开、部分失败”也属于这一类。
  2. **应用自己的往返次数**：邀请页首屏要等约 5 次串行往返，每次都要跨越高延迟链路。这一类**可以优化，且收益最大**。
- 所以策略是：**少一次往返，比让每次往返更快更值**。

## 现状瓶颈（均已对照 `main` 复核）

### 首屏链路（打开 `#/i/<token>`）
1. `index.html`
2. 主 JS/CSS（`index-*.js`）
3. 主 JS 执行后才动态 `import('./invitation')`（以及它依赖的 `ui`、`booking` 分包和样式）
4. `GET /api/invite`
5. 等 4 返回、DOM 建好后，才发 `GET /api/invite/calendar?week=0`

即 4 与 5 串行，3 与 4 也串行，中间是空白或“正在读取周历…”。

### API 侧（`server/invites.ts`、`server/booking.ts`）
- `GET /api/invite`：先查邀请（`token_hash` 有唯一索引），再 `UPDATE invites SET last_opened_at…`。**GET 里有写入**，且阻塞响应。（M5 的 PR #1 还会在其后再串一次个人内容查询。）
- `GET /api/invite/calendar`：`activeInvitation`（1 次）→ `readRules`（1 次）→ 并行 6 个查询 → 若开了城市行程再 2 次城市查询。约 **3 段串行、最多约 10 次 D1 查询**，每次 Worker 到 D1 都是一次往返。
- `readAvailability` 把两个日历源完整的 `busy_json`（覆盖约 30 天、每源最多 1024 段）读出来再在 Worker 里 `JSON.parse`，而响应只需要一周。
- 响应体包含 7 天 × 24 个槽对象（上百个），客户端本来就能用 `requestWeek` 自己生成网格，只需要“忙闲叠加层”。
- 全部响应 `Cache-Control: no-store`（个人数据应保持）；但**静态资源也没有设置缓存头**：`web/public/_headers` 里只有安全头。

### 部署配置（`scripts/configure-worker.mjs`、`scripts/prepare-m1.mjs`）
- 没有设置 `placement`（Smart Placement）。
- D1 创建时 `primary_location_hint: 'apac'`，主库在亚太；而 Worker 在**用户就近的节点**运行，若节点离主库远，每次 D1 查询都跨区。
- `observability.enabled: false`，因此没有延迟数据。
- 每 5 分钟的日历同步 cron 有 CPU 超限风险（见文末）。

### 前端渲染
- 每次选时段、切视图、翻周、30 分钟走时都会整表 `innerHTML` 重绘（约 168 个槽）。
- 翻周每次都重新请求，返回已看过的一周也重取。
- 邀请路由引入了整份 `admin.css`；`connectivity` 模块被打进主包但只有 `#/check` 用到。

## 建议清单（按优先级）

### 第 0 步：先测量（半小时，必做）
目的：确认瓶颈是往返次数还是网络路径，避免盲改。
- 用浏览器 DevTools（Network + Performance）在 2–3 种网络下录一次 `#/i/<token>` 首屏，记录每个请求的 TTFB。
- 在终端用 `curl -w '%{time_connect} %{time_starttransfer} %{time_total}\n' -o /dev/null -s -H 'Authorization: Bearer …' https://book-my-time-patrick.cn/api/invite` 对比不同网络。
- 需要服务端耗时时，**临时**把 `observability.enabled` 改为 `true`（带较低采样率），测完改回。README 里的隐私承诺是“默认关闭请求观测日志”，打开前请确认可接受，并以 Cloudflare 官方文档为准核对日志包含的字段。
- 同时检查静态资源响应头：`curl -sI https://book-my-time-patrick.cn/assets/<某个哈希文件>`，看是否有 `cache-control`。

### 第 1 步：零风险配置（预期有效，几乎不改代码）
| 项 | 做法 | 预期 | 风险 |
| --- | --- | --- | --- |
| 静态资源长缓存 | `web/public/_headers` 增加 `/assets/*` → `Cache-Control: public, max-age=31536000, immutable`；`index.html` 保持每次校验 | 回访者省掉每个哈希文件的一次校验往返 | 极低。文件名带哈希，更新即换名 |
| Smart Placement | 生成的 `wrangler` 配置加 `"placement": {"mode": "smart"}` | 让 Worker 靠近亚太的 D1，把“多次 D1 往返”变成近距离往返 | 低。需 A/B 对比首字节；静态资源不受影响。可随时回退 |
| 邀请页不引入 `admin.css` | 把邀请页用到的样式拆出 | 少下载一份无关 CSS | 低（纯构建/样式） |

### 第 2 步：前端并行化（收益最大，改逻辑，需要你确认）
| 项 | 做法 | 预期 |
| --- | --- | --- |
| 与动态加载并行取数 | 路由识别到邀请链接时，**立刻**同时发起 `import('./invitation')`、`GET /api/invite` 和 `GET /api/invite/calendar?week=0` | 首屏由约 5 次串行降到约 2 次（HTML/JS 一轮 + 并行数据一轮） |
| 先画通用周网格 | 数据未回时用 `requestWeek` 直接渲染灰色骨架（代码里翻周时已经这么做） | 感知速度明显提升，几乎不依赖网络 |
| 周缓存 + 预取 | 按周偏移缓存响应（受 `validUntil` 约束），空闲时预取下一周 | 翻周瞬时，返回已看周不再请求 |
| 自动重试一次 | 对 `/api/invite` 失败做一次带退避的重试 | 缓解大陆网络的偶发失败 |
| 去掉门禁页闪现 | 邀请路由先画骨架再换内容（见 `预约流程优化建议.md` #4） | 不再像“被拒绝” |

### 第 3 步：服务端少往返（中等收益，改逻辑 + 补测试）
| 项 | 做法 | 预期 / 风险 |
| --- | --- | --- |
| `GET /api/invite` 去掉阻塞写入 | `last_opened_at/open_count` 用 `c.executionCtx.waitUntil` 异步写，或像 `requireAdmin` 那样限频（每分钟最多一次） | 少一次阻塞往返。注意：现有逻辑用这次 UPDATE 同时再确认邀请未撤销/未过期，改动时要保留校验语义并补测试 |
| 合并 `/api/invite` 与 `/api/invite/calendar` | 首次加载走一个接口返回“邀请信息 + 当前周日历” | 再省一次往返；接口契约有变，需要谨慎 |
| 日历多段查询用 `db.batch` 合并 | 把 `readRules`、城市等并入第一批并行查询，或用一次 `batch` 提交 | 约 3 段串行降到约 1–2 段 |
| 响应瘦身 | 不返回 168 个槽，只返忙闲区间和开放局；`busy_json` 按周裁剪 | 减少 D1 读取量和响应体 |

### 第 4 步：可选缓存（需要更谨慎）
- **非个人化的忙闲快照**可用 Cache API 或 Worker 内存缓存 30–60 秒。提交预约时服务端本来就会重新校验冲突，所以短暂缓存不会造成超卖，但会让“刚被占用”的时段晚几十秒显示。是否可接受取决于你。
- D1 读副本（Sessions API）：代码里直接用 `db.prepare`，且 GET 里有写入；只有当 Worker 与副本确实就近时才有意义，**不建议优先做**。

## 免费套餐下做不到的事
- **改善大陆到 Cloudflare 的网络路径**：Cloudflare China Network 需要企业版并要求备案。你已选择暂不备案，所以这部分只能接受，靠“少往返”来缓解。不建议使用第三方“优选 IP”之类的方案，稳定性与合规都不可控。
- **提高 Worker CPU 上限**：免费套餐为每次调用约 10ms CPU；之前 Argon2id 在这个上限下失败过（见 `docs/M0-线上验证记录.md`），所以才改用通行密钥。
- **提高 D1 免费额度**（读 500 万行/天、写 10 万行/天）：目前个人使用量远低于此，但 `busy_json` 全量读取会放大“读行数”，瘦身后更安全。
- **子请求上限**：免费版每次调用 50 个。当前最重的接口约 10 次 D1 调用，余量足够。

## 风险提醒
- **日历同步 cron（每 5 分钟）**：解密、请求 CalDAV/Graph、XML 解析、合并最多 1024 段，在 10ms CPU 内有可能超限（错误 1102）。一旦超限，快照 10 分钟后过期，访客会看到“暂不可用”。目前没有观测到，但也没有监控。建议第 0 步临时开观测时顺便看这一项的 CPU 时间。
- 任何缓存/并行改动都要保持“邀请撤销、过期立即生效”和“预览不计访问、不写数据”这两条既有规则。

## 建议的执行顺序
1. 第 0 步测量（半小时）。
2. 第 1 步三项配置（不改应用逻辑，可当天做，随时可回退）。
3. 第 2 步前端并行化 + 骨架（体验提升最大），配合视觉改版一起做最省事。
4. 第 3 步按测量结果挑做。
5. 第 4 步仅在仍然不满意时考虑。

## 需要你决定的
- 是否同意临时打开观测日志做测量（会记录请求元数据，测完关闭）。
- 第 2、3 步涉及逻辑改动，是否在视觉方案定稿后一起做，还是单独排期。
